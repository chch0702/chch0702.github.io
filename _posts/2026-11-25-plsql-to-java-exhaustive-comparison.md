**한 줄 요약**: 레거시 로직 전환에서 시간이 드는 건 코드를 옮기는 일이 아니라 "옮긴 결과가 정말 같다"를 증명하는 일이었다. 경우의 수가 유한하다면, 샘플 몇 개보다 전부 비교하는 쪽이 싸고 확실하다.

---

## 들어가며

회사에서 업무 시스템을 개발·운영하고 있다. 오래된 시스템이 대개 그렇듯, 업무 로직의 상당 부분이 Oracle PL/SQL 프로시저와 함수 안에 있다.

최근 결재 로직을 Spring 기반 Java 모듈로 옮겼다. 결재 건의 상태와 결재 단계, 사용자 역할에 따라 "지금 이 사람이 어떤 버튼을 누를 수 있는지"를 정하는 로직이다. 여러 개의 프로시저와 권한 함수에 걸쳐 있었다.

옮기는 이유는 단순했다. **바꾸기 무섭고, 시험하기 어려웠다.** 버튼 하나의 권한 조건을 바꾸려 해도 프로시저 안의 분기를 머릿속으로 따라가야 했고, 확인 방법은 개발 DB에서 몇 가지 경우를 직접 돌려 보는 것뿐이었다.

## 1. 프로시저 안에는 문서에 없는 규칙이 산다

분석해 보니 결재 권한 판단에는 담당자 확인 단계만 십수 개, 결재 단계별 버튼도 여러 종류가 있었다. 그리고 "이건 왜 이렇지?" 싶은 분기가 10여 군데 나왔다.

```sql
-- 예시 코드 (실제 코드 아님)
IF v_status = 'RETURNED' AND v_step >= 3 THEN
   v_can_approve := 'N';
ELSIF v_role = 'MANAGER' AND v_is_delegate = 'Y' THEN
   v_can_approve := 'Y';   -- 위임자는 단계와 상관없이 승인 가능?
END IF;
```

이런 분기를 만나면 세 가지로 나눴다.

| 분류 | 뜻 | 처리 |
|---|---|---|
| 살아있는 규칙 | 지금도 업무에서 필요 | 이름 붙여서 도메인 메서드로 |
| 흔적 | 제도·정책 변경 후 사실상 안 타는 분기 | 데이터로 안 타는지 확인한 뒤 제거 후보로 |
| 모름 | 이유를 못 찾음 | **동작은 그대로 옮기고** 기록, 현업 확인 목록으로 |

이 분기들은 전부 "모름"으로 분류해서 **동작을 바꾸지 않고** 옮겼다. 전환 작업의 목표는 개선이 아니라 동등성이다. 이상해 보이는 동작을 그 자리에서 "고치면", 그건 전환이 아니라 몰래 하는 기능 변경이 된다.

## 2. 구조: 바꾸기 쉽게, 되돌리기 쉽게

새 모듈은 포트·어댑터(헥사고날) 구조로 나눴다.

```
approval/
├─ api/            컨트롤러, 요청·응답
├─ application/    유스케이스 (조회, 승인)
├─ domain/         결재 상태·단계·권한 규칙 ← 핵심. DB를 모른다
├─ port/           DB 조회 인터페이스
└─ infra/          JdbcClient 기반 구현
```

핵심은 **권한 규칙을 DB에서 떼어 낸 순수 함수로 만드는 것**이었다. 입력(상태, 단계, 역할, 위임 여부…)을 넣으면 버튼 목록이 나오는 함수다. 그래야 DB 없이 시험할 수 있다.

그리고 설정 스위치 하나로 **기존 프로시저 경로로 즉시 되돌릴 수 있게** 했다. 운영에서 하나라도 이상하면 코드 배포 없이 원래대로 돌아가는 길이다. 되돌릴 길을 먼저 만들면 반영하는 날의 긴장이 절반으로 준다.

## 3. 검증: 참조 구현과 전수 비교

이번 작업의 핵심이다.

### 왜 샘플이 아니라 전수인가

권한 로직의 입력은 대부분 **유한한 열거값**이다. 상태 몇 개, 단계 몇 개, 역할 몇 개, 예/아니오 플래그 몇 개. 곱해 보면 크지만 셀 수 있는 수다. 이번에는 프로시저·권한 함수 쪽이 수백만 조합, 버튼 권한 쪽이 그보다 훨씬 많아서 합치면 **약 1억 조합**이었다.

1억이면 많아 보이지만, 순수 함수 두 개를 비교하는 데는 노트북에서 수 분이면 끝난다. 반면 사람이 고른 샘플 50개는 "내가 생각한 경우"만 확인한다. 레거시의 버그와 특이점은 대개 **내가 생각하지 못한 경우**에 숨어 있다.

### 참조 구현이란

원본 PL/SQL을 **해석하지 않고 줄 단위로 그대로** Java로 옮긴 코드다. 보기 좋게 다듬지도, 중복을 없애지도 않는다. 원본의 IF 순서까지 그대로 둔다. 이게 "정답지" 역할을 한다.

그다음 새 구조로 깔끔하게 다시 쓴 도메인 코드를 만들고, 두 구현에 **모든 입력 조합**을 넣어 결과를 비교한다.

```java
// 예시 코드 — 구조만 보여주기 위해 새로 작성
@Test
void 모든_조합에서_참조구현과_새구현의_결과가_같다() {
    long checked = 0;
    List<String> diffs = new ArrayList<>();

    for (Status s : Status.values())
      for (int step = 0; step <= MAX_STEP; step++)
        for (Role r : Role.values())
          for (boolean delegate : new boolean[]{true, false})
            for (boolean urgent : new boolean[]{true, false}) {
                var in = new ApprovalInput(s, step, r, delegate, urgent);
                var expected = LegacyReference.buttons(in);   // 원본 직역
                var actual   = ApprovalPolicy.buttons(in);    // 새 구현
                checked++;
                if (!expected.equals(actual) && diffs.size() < 20) {
                    diffs.add(in + " expected=" + expected + " actual=" + actual);
                }
            }

    assertThat(diffs).as("불일치 %d건 중 앞 20건 / 전체 %d조합", diffs.size(), checked).isEmpty();
}
```

포인트 몇 가지.

- **불일치를 처음 하나에서 멈추지 말고 모아서 보여준다.** 20건만 보면 대개 패턴이 보인다.
- 입력 범위(`MAX_STEP` 등)는 **원본에서 실제로 쓰는 값의 한계를 근거로** 정한다. 범위를 좁게 잡으면 전수 비교가 아니다.
- 조합이 너무 많으면 서로 독립적인 축을 나눠서 따로 전수 비교한다. 이번에도 프로시저 쪽과 버튼 쪽을 나눠서 돌렸다.

### 결과: 불일치 0건, 그런데 시험이 잡아낸 것 2건

최종 결과는 불일치 0건이었다. 그런데 0건이 되기까지 시험이 잡아낸 오류가 두 개 있었다.

1. **원본을 옮겨 적는 과정의 오류.** 참조 구현을 만들면서 원본 조건 하나를 잘못 옮겼다. 새 구현은 맞게 짰는데 "정답지"가 틀려 있었다.
2. **참조 구현 자체의 오류.** 원본의 NULL 비교 동작을 Java에서 다르게 처리하고 있었다.

여기서 배운 점이 있다. **직역한 정답지도 틀릴 수 있다.** 그래서 마지막 단계로, 개발 DB에서 원본 프로시저를 실제로 실행한 결과와 대조하는 시험을 남겨 두었다. 원본 실행 결과, 참조 구현, 새 구현이 셋 다 일치해야 진짜 끝이다.

## 4. PL/SQL을 Java로 옮길 때 자주 걸리는 곳

이번 작업과 이전 이관 작업에서 실제로 걸렸던 것들이다.

| 함정 | PL/SQL | Java에서 주의할 점 |
|---|---|---|
| 빈 문자열 | Oracle에서 `''`는 `NULL` | `"".equals(x)`와 `x == null`을 같은 경우로 다뤄야 할 때가 있다 |
| NULL 비교 | `NULL = NULL`은 참이 아님, `IF` 조건이 NULL이면 ELSE로 감 | `Objects.equals`는 null끼리 같다고 본다. 원본이 ELSE로 가는지 확인 |
| 반올림·절사 | `ROUND`, `TRUNC` | `BigDecimal` + `RoundingMode.HALF_UP` / `DOWN`을 명시 |
| 날짜 | `ADD_MONTHS`의 말일 보정, `LAST_DAY` | `LocalDate.plusMonths()`와 말일 처리 결과가 다른 경우 확인 |
| CHAR 비교 | 고정 길이 CHAR는 뒤 공백을 채움 | `trim()` 여부를 원본 컬럼 타입 기준으로 결정 |
| 암묵적 형변환 | `'1' = 1`이 통과 | Java는 타입이 다르면 다름. 원본이 어떤 타입으로 비교했는지 확인 |

이 표의 대부분은 샘플 시험으로는 잘 안 걸린다. NULL이나 빈 값, 경계 날짜 같은 **입력의 가장자리**에서만 드러나기 때문이다. 전수 비교가 강한 이유도 여기에 있다.

## 5. 배운 것

1. **변환은 쉽고, 검증이 일이다.** 체감으로는 분석 3, 변환 2, 검증 5였다.
2. **이상한 동작은 고치지 말고 기록하라.** 전환과 개선을 한 번에 하면, 문제가 생겼을 때 어느 쪽 탓인지 알 수 없다.
3. **경우의 수가 유한하면 전부 비교하라.** 샘플은 내 생각을 확인하고, 전수는 내가 모르는 것을 찾아 준다.
4. **정답지도 검증하라.** 직역 구현 → 원본 실행 결과 대조까지 가야 끝이다.
5. **되돌릴 길을 먼저 만들어라.** 설정 스위치 하나가 반영일의 판단을 훨씬 쉽게 만든다.

## 마치며

레거시 전환을 이야기할 때 흔히 "무엇으로 옮길까"에 관심이 쏠린다. 그런데 실제로 해 보면 어려운 질문은 "옮긴 게 똑같다는 걸 어떻게 아느냐"였다. 이 질문에 숫자로 답할 수 있으면, 반영하는 날 자신 있게 버튼을 누를 수 있다.

다음 글에서는 같은 원칙을 플랫폼 전환에 적용한 이야기를 써 보려 한다. 구형 WAS와 JDK 위의 웹 서비스를 최신 Java와 Jakarta EE로 옮기면서, 리허설과 전수 시험표로 무장애 운영 전환까지 간 과정이다.
