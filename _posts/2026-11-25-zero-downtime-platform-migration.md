**한 줄 요약**: 플랫폼 전환에서 장애를 막아 준 건 새 기술이 아니라 "무엇이 같아야 하는지"를 전부 적은 시험표와, 그 시험표로 여러 번 해 본 리허설이었다. 전환 당일은 리허설을 한 번 더 하는 날이어야 한다.

---

## 들어가며

[지난 글]({% post_url 2026-11-25-plsql-to-java-exhaustive-comparison %})에서는 결재 로직을 옮기면서 "옮긴 결과가 정말 같다"를 전수 비교로 증명한 이야기를 했다. 이번에는 같은 원칙을 더 큰 단위, **플랫폼 전환**에 적용한 이야기다.

회사 업무 시스템 중에 지원 종료가 다가온 구형 WAS와 오래된 JDK, 구버전 Spring 위에서 돌아가는 웹 서비스 두 개가 있었다. 이것을 JDK 21, Jakarta EE 9(Servlet 5·JSP 3), Spring 6과 Spring Boot 3(WAR 배포) 조합으로 옮기고, 새 WAS 위에서 운영을 시작하는 일이었다. 분석부터 운영 전환까지 혼자 맡았다.

조건은 하나였다. **사용자 입장에서 아무것도 달라지면 안 된다.** 화면도, 응답도, 다른 시스템과 주고받는 결과도 그대로여야 했다.

## 1. 전환이 어려운 이유: "같아야 하는 것"이 너무 많다

코드 변환 자체는 생각보다 기계적이다. `javax.*` 패키지를 `jakarta.*`로 바꾸고, JDK 21에서 사라진 API를 대체하고, 빌드 설정을 새 버전에 맞추면 일단 컴파일은 된다. (이 부분의 실제 체크리스트는 다음 글에서 따로 정리한다.)

어려운 건 그다음이다. 컴파일이 되고 서버가 뜬다고 끝이 아니다. 실제로 문제가 된 건 이런 것들이었다.

- **새 WAS의 기본 동작 차이.** 같은 서블릿 스펙인데도 WAS마다 기본값이 다르다. 요청 처리 순서, 기본 문자셋, 정적 자원 처리 방식 같은 것들.
- **문자셋 차이.** JDK 버전이 바뀌면서 기본 문자셋이 달라지는 부분이 있다(JDK 18부터 기본값이 UTF-8). 문자열을 바이트로 바꾸는 코드가 문자셋을 명시하지 않았다면 결과가 조용히 달라진다.
- **구 WAS가 대신 해 주던 일.** 예전 WAS 설정으로 처리하던 일부 기능은 새 WAS로 가면 사라진다. 이런 건 앱 쪽 서블릿 필터로 다시 만들어야 했다.

공통점은 **에러가 나지 않는다**는 것이다. 서버는 잘 뜨고 화면도 열린다. 다만 어딘가의 결과가 미묘하게 다르다. 그래서 "잘 뜨는지"가 아니라 "같은지"를 확인하는 방법이 필요했다.

```java
// 예시 코드 — 새로 작성
// 나쁜 예: 기본 문자셋에 의존 → JDK 버전이나 실행 옵션에 따라 결과가 달라진다
byte[] bytes = text.getBytes();

// 좋은 예: 문자셋을 명시 → 어디서 돌려도 같은 결과
byte[] bytes = text.getBytes(StandardCharsets.UTF_8);
```

## 2. 전수 시험표: 화면·자원·기능을 전부 적는다

먼저 한 일은 **"같아야 하는 것"의 목록**을 만드는 것이었다. 샘플이 아니라 전부.

| 구분 | 적은 것 | 확인 방법 |
|---|---|---|
| 화면 | 모든 화면 주소 | 열리는지, 기존과 같은 내용이 나오는지 |
| 정적 자원 | CSS·JS·이미지 경로 | 응답 코드, 내용이 같은지 |
| 기능 | 조회·저장·파일 처리·외부 연계 등 기능 단위 | 같은 입력에 같은 결과인지 |
| 설정 | 환경별 설정값, 로그 위치, 문자셋 | 기대값과 일치하는지 |

규모는 화면 수십 개, 기능 백여 개였다.

이 표가 중요한 이유는 두 가지다.

1. **완료 기준이 생긴다.** "다 된 것 같다"가 아니라 "표의 모든 줄이 통과했다"로 끝을 정할 수 있다.
2. **반복할 수 있다.** 같은 표를 개발 서버, 시험 서버, 리허설, 전환 당일에 똑같이 돌린다. 매번 같은 잣대로 잰다.

표의 상당 부분은 자동 시험으로 바꿨다. 화면과 자원은 주소 목록을 돌면서 응답을 확인하고, 설정은 기대값과 비교하고, 결과는 엑셀 보고서로 남겼다. 단위 시험도 수백 건 만들었다.

```java
// 예시 코드 — 새로 작성
// 화면·자원 주소 목록을 돌면서 기존 서버와 새 서버의 응답을 비교하는 단순한 시험
@ParameterizedTest
@MethodSource("pagePaths")
void 기존_서버와_새_서버의_응답이_같다(String path) throws Exception {
    var oldRes = http.send(get(OLD_BASE + path), ofString());
    var newRes = http.send(get(NEW_BASE + path), ofString());

    assertThat(newRes.statusCode()).as(path).isEqualTo(oldRes.statusCode());
    assertThat(normalize(newRes.body())).as(path).isEqualTo(normalize(oldRes.body()));
}

// 세션 ID·날짜처럼 매번 바뀌는 값은 비교 전에 지운다
static String normalize(String body) {
    return body.replaceAll("jsessionid=[^\"&;]+", "jsessionid=X")
               .replaceAll("\\d{4}-\\d{2}-\\d{2} \\d{2}:\\d{2}:\\d{2}", "<시각>");
}
```

포인트는 `normalize`다. 매번 달라지는 값을 지우지 않으면 모든 시험이 실패해서, 진짜 차이를 찾을 수 없다. 반대로 너무 많이 지우면 진짜 차이도 같이 지워진다. 무엇을 지울지는 하나씩 이유를 적어 두었다.

## 3. 리허설: 전환 절차서를 여러 번 고친다

시험표가 "무엇을 확인할지"라면, 런북(전환 절차서)은 "어떤 순서로 할지"다.

런북에는 이런 것을 적었다.

- 단계마다 **할 일, 확인할 것, 실패하면 할 일**
- 각 단계의 예상 소요 시간
- 되돌리기(롤백) 절차와 "여기까지 오면 되돌린다"는 판단 기준

그리고 운영과 비슷하게 꾸민 환경에서 이 런북을 그대로 따라 하는 리허설을 반복했다. 리허설을 할 때마다 런북이 틀린 곳이 나왔다. 순서가 잘못된 단계, 빠진 확인, 생각보다 오래 걸리는 작업. 그때마다 런북을 고쳤고, 결국 10번 넘게 고쳤다.

리허설에서 배운 것 하나: **리허설은 성공하려고 하는 게 아니라 런북의 틀린 곳을 찾으려고 하는 것이다.** 리허설에서 막히면 실패가 아니라 수확이다. 전환 당일에 막히는 것보다 훨씬 싸다.

## 4. 되돌릴 길과 장애 대비

1편에서 "되돌릴 길을 먼저 만들라"고 했는데, 플랫폼 전환에서는 이게 더 중요하다.

- **기존 환경을 지우지 않는다.** 새 환경이 안정될 때까지 기존 환경은 그대로 두고, 연결만 바꿔서 되돌릴 수 있게 했다.
- **설정은 바꾸기 전에 백업하고, 바꾼 뒤에 비교한다.** 설정 파일의 지문(해시)을 남겨서, 의도한 곳만 바뀌었는지 확인했다.
- **되돌리기도 리허설한다.** 롤백 절차는 써 두기만 하면 당일에 안 돌아갈 수 있다. 리허설 때 되돌리기까지 실제로 해 보고 걸리는 시간을 런북에 적었다.

이 중 무엇도 화려한 기술은 아니다. 다만 하나라도 없으면 전환 당일 판단이 어려워진다. "되돌릴 수 있다"는 확신이 있어야 "진행한다"는 결정도 빨라진다.

## 5. 전환 당일

당일은 런북을 따라 갔다. 리허설을 충분히 한 덕분에 대부분은 예상대로 흘러갔다. 그래도 리허설 환경에는 없던 설정 문제가 하나 나왔는데, 런북의 "실패하면 할 일"과 확인 목록 덕분에 원인을 빨리 좁혀서 사용자에게 영향이 가기 전에 바로 해결했다. 완벽한 리허설은 없다. 다만 리허설을 많이 할수록 당일에 새로 만나는 문제는 하나로 줄고, 그 하나에 집중할 여유가 생긴다.

결과는 이랬다.

- 전환 전 자동 시험 오류 0건
- 전환 후 장애 0건

두 번째 서비스는 더 까다로웠다. 첫 번째 서비스가 이미 새 WAS에서 운영 중이었기 때문에, **운영 중인 서비스를 멈추지 않고** 같은 WAS에 올려야 했다. 방법은 같았다. 기존 서비스가 계속 정상인지 확인하는 시험을 시험표에 더하고, 전환 절차를 미리 두 번 모의로 돌려 본 뒤 옮겼다. 첫 번째 서비스는 멈추지 않았고, 두 번째 서비스도 전환 후 장애 없이 운영을 시작했다.

## 6. 배운 것

1. **"잘 뜬다"와 "같다"는 다르다.** 플랫폼 전환의 문제는 대부분 에러 없이 결과만 다르게 나온다. 확인 기준을 "같은지"로 잡아야 한다.
2. **같아야 하는 것을 전부 적어라.** 시험표가 있으면 완료 기준이 생기고, 같은 잣대로 몇 번이고 다시 잴 수 있다.
3. **기본값에 기대지 마라.** 문자셋, WAS 설정 같은 기본값은 버전과 제품에 따라 바뀐다. 중요한 것은 명시한다.
4. **리허설은 런북의 틀린 곳을 찾는 시간이다.** 막힐수록 당일이 쉬워진다.
5. **되돌릴 길이 진행 결정을 빠르게 한다.** 기존 환경 보존, 설정 백업·비교, 되돌리기 리허설.

## 마치며

로직 전환이든 플랫폼 전환이든, 결국 같은 질문으로 돌아온다. "옮긴 게 똑같다는 걸 어떻게 아느냐." 로직은 입력 조합을 전부 비교해서 답했고, 플랫폼은 화면·자원·기능을 전부 적은 시험표와 반복 리허설로 답했다. 전수로 확인할 수 있는 건 전수로 확인하는 것, 그게 두 작업의 공통점이었다.

다음 글에서는 이번 전환에서 실제로 걸렸던 것들을 체크리스트로 정리한다. `javax` → `jakarta` 패키지 변환, JDK 8 → 21에서 사라진 API, Spring 6·Boot 3로 올릴 때 주의할 점들이다.
